\subsection{Conceitos Fundamentais em Pílulas Práticas de Aquecimento}

Antes de iniciarmos a construção da arquitetura completa da Vitrine Comunitária (que integrará banco de dados relacional persistente, camadas modulares em ES6 e contingência offline), realizaremos \textbf{4 mini-práticas guiadas de aquecimento}. 

Cada pílula introduz um conceito arquitetural isolado e fornece o código \textbf{100\% completo} para ser executado imediatamente pelos estudantes no laboratório em poucos minutos.

\vspace{0.2cm}
\begin{tcolorbox}[colback=azulObjetivos!5, colframe=azulObjetivos, title=\textbf{Padrão Arquitetural: Separação de Arquivos e Ciclo de Vida do DOM}, arc=3pt]
\textbf{1. Separação de Responsabilidades (HTML vs. JS):}
Seguindo a mesma lógica pedagógica aplicada ao longo do curso (Roteiro 02 com manipulação de eventos, Roteiro 04 com camadas modulares), manteremos os arquivos JavaScript estritamente separados em arquivos externos dedicados (\texttt{functions.js}). O arquivo \texttt{index.html} gerencia apenas a marcação estrutural e folhas de estilo, enquanto \texttt{functions.js} concentra a lógica comportamental e requisições assíncronas.

\vspace{0.15cm}
\textbf{2. O Desafio do Ciclo de Vida do DOM (\textit{Race Conditions}):}
Quando incluímos um script no cabeçalho (\texttt{<head>}) de forma tradicional, o navegador interrompe o processamento do documento HTML para baixar e executar o arquivo JavaScript imediatamente. Nesse momento, os elementos visuais da interface (como \texttt{<button id="btnCarregar">} e formulários) \textbf{ainda não existem na árvore do DOM}. Caso o script tente acessá-los diretamente, o retorno será \texttt{null}, resultando no erro clássico:
\begin{center}
\small\texttt{\textcolor{vermelhoCodigo}{Uncaught TypeError: Cannot read properties of null (reading 'addEventListener')}}
\end{center}

\vspace{0.15cm}
\textbf{3. A Solução em Duas Camadas (\texttt{defer} + \texttt{DOMContentLoaded}):}
Para garantir um ciclo de vida 100\% seguro e resiliente:
\begin{itemize}[leftmargin=*]
  \item \textbf{No HTML:} Utilizamos o atributo \textbf{\texttt{defer}} na tag de inclusão: \texttt{<script src="functions.js" defer></script>}. O \texttt{defer} instrui o navegador a carregar o script em segundo plano sem travar o HTML, adiando sua execução até que o parse do documento seja concluído.
  \item \textbf{No JavaScript:} Envolvemos o mapeamento dos nós e a vinculação de ouvintes no evento \textbf{\texttt{DOMContentLoaded}}:
\begin{verbatim}
document.addEventListener('DOMContentLoaded', () => {
    // Nós mapeados e eventos registrados com a árvore DOM 100% pronta!
});
\end{verbatim}
\end{itemize}
\end{tcolorbox}

\subsubsection{Pílula 1: Assincronismo e Leitura de Dados com Fetch API (GET)}

\textbf{Fundamentação Teórica:} No JavaScript tradicional, operações de rede não podem ser executadas de forma síncrona (\textit{bloqueante}), pois o navegador congelaria a interface enquanto aguardasse a resposta de outro computador. 

Por isso, o JavaScript moderno utiliza o mecanismo de \textbf{Promises} (promessas de valores futuros) manipuladas pelas palavras-chave \textbf{\texttt{async}} e \textbf{\texttt{await}}. A função global \textbf{\texttt{fetch(url)}} dispara uma requisição HTTP assíncrona. Quando a resposta do servidor chega, utilizamos o método \textbf{\texttt{await resposta.json()}} para converter o fluxo de texto HTTP em um objeto ou vetor JavaScript utilizável.

\begin{boxAtividade}[Mini-Exemplo 1: Leitura Assíncrona de Arquivo JSON com Fetch GET]
\textbf{Objetivo Prático:} Ler um vetor de serviços em formato JSON e preencher dinamicamente uma lista HTML na tela sem recarregar a página, com script externo e controle do DOM.
\end{boxAtividade}

\newpage
\textbf{Passo 1.3: Criar a lógica assíncrona desacoplada (\texttt{mini-exemplos/01-fetch-get/functions.js}):}
\begin{boxCodigoJS}
// 1. Função assíncrona dedicada com nome claro
async function carregarServicos(listaServicos) {
  try {
    // Passo 1.1: Dispara a requisição HTTP assíncrona para o arquivo
    const resposta = await fetch('dados.json');

    // Passo 1.2: Converte a resposta em formato JSON para um vetor JavaScript
    const servicos = await resposta.json();

    // Passo 1.3: Limpa a lista antes de adicionar novos elementos
    listaServicos.innerHTML = '';

    // Passo 1.4: Percorre a lista e cria os elementos no DOM
    for (const servico of servicos) {
      const item = document.createElement('li');
      item.className = 'list-group-item d-flex justify-content-between align-items-center';
      item.innerHTML = `
        <span>${servico.nome}</span>
        <span class="badge bg-success rounded-pill">R$ ${servico.preco.toFixed(2)}</span>
      `;
      listaServicos.appendChild(item);
    }

  } catch (erro) {
    console.error('Falha ao carregar os dados do arquivo:', erro);
  }
}

// 2. Controle do ciclo de vida: executa quando o DOM estiver completamente pronto
document.addEventListener('DOMContentLoaded', () => {
  const btnCarregar = document.getElementById('btnCarregar');
  const listaServicos = document.getElementById('listaServicos');

  btnCarregar.addEventListener('click', () => carregarServicos(listaServicos));
});
\end{boxCodigoJS}

\subsubsection{Pílula 2: Microbackend Flask e a Política de Mesma Origem (CORS)}

\textbf{Fundamentação Teórica: O que é o Microframework Flask e Como Funciona}

Em uma arquitetura web desacoplada moderna, os dados não residem em arquivos estáticos locais no navegador, mas sim em um servidor backend remoto que expõe uma API RESTful. Na linguagem Python, uma das ferramentas mais consagradas e eficientes para essa finalidade é o microframework \textbf{Flask}.

\textbf{1. O que é o Flask?}
Criado em 2010 por Armin Ronacher (mantido pelo coletivo de código aberto \textit{Pallets Projects}), o Flask é classificado como um \textbf{microframework web}. O termo \textit{"micro"} não significa que ele seja limitado ou frágil; pelo contrário, expressa uma filosofia de design intencional: manter um \textbf{núcleo enxuto e minimalista} (\textit{lean core}), sem impor decisões arquiteturais rígidas ao desenvolvedor.
\begin{itemize}[leftmargin=*]
  \item \textbf{Contraste Didático (Flask vs. Django):} Enquanto frameworks full-stack monolíticos (como o Django) seguem a filosofia \textit{"baterias inclusas"} --- trazendo nativamente camadas obrigatórias de ORM, painéis de administração prontos e geradores de formulários complexos ---, o Flask entrega apenas o estritamente indispensável: o motor de roteamento e despacho HTTP (baseado na biblioteca \textit{Werkzeug}) e o motor de renderização de modelos (\textit{Jinja2}). O programador é 100\% livre para escolher seu banco de dados, bibliotecas de validação e arquitetura de pastas.
\end{itemize}

\textbf{2. Para quais tipos de aplicações o Flask serve?}
Pela sua leveza, rapidez de inicialização e baixo consumo de recursos, o Flask é a escolha ideal para:
\begin{itemize}[leftmargin=*]
  \item \textbf{APIs RESTful desacopladas:} Prover endpoints JSON consumidos por aplicações web ricas (\textit{Single Page Applications} - SPAs em React, Vue, Angular ou JavaScript Puro) e aplicativos mobile.
  \item \textbf{Microsserviços:} Componentes distribuídos especializados que resolvem tarefas pontuais em nuvem (ex: serviço de envio de e-mails, processamento de pagamentos).
  \item \textbf{Prototipagem Ágil e MVPs (\textit{Minimum Viable Products}):} Permite construir uma API comercial completa em poucos minutos em um único arquivo \texttt{.py}.
  \item \textbf{Serviços de Inteligência Artificial e Ciência de Dados:} É o padrão de mercado para empacotar modelos de \textit{Machine Learning} e \textit{Deep Learning} (Scikit-Learn, PyTorch, TensorFlow) e disponibilizá-los na internet como serviços preditivos consumíveis via HTTP.
\end{itemize}

\textbf{3. Como o Flask funciona (Arquitetura e Ciclo de Vida)?}
O Flask baseia-se na especificação padrão \textbf{WSGI} (\textit{Web Server Gateway Interface} - PEP 3333), que define como um servidor web se comunica com programas Python:
\begin{enumerate}[leftmargin=*]
  \item \textbf{Instanciação da Aplicação:} Cria-se o objeto central via \texttt{app = Flask(\_\_name\_\_)}.
  \item \textbf{Mapeamento Declarativo com Decoradores:} As rotas da API são declaradas através de decoradores Python: \texttt{@app.route('/caminho', methods=['GET', 'POST'])}. Esse padrão associa um endereço URL e um verbo HTTP diretamente a uma função executável (\textit{view function}).
  \item \textbf{Ciclo de Requisição e Resposta:} Quando o navegador dispara uma requisição HTTP, o Flask a intercepta, processa parâmetros da URL ou corpo (JSON), executa a função mapeada e despacha uma resposta HTTP padronizada de volta ao cliente.
  \item \textbf{Serialização JSON Nativa (\texttt{jsonify}):} Em APIs REST, as respostas são trafegadas em formato JSON. O utilitário nativo \texttt{jsonify()} converte dicionários e listas Python em strings formatadas em JSON e anexa automaticamente o cabeçalho \texttt{Content-Type: application/json; charset=utf-8}.
\end{enumerate}

\textbf{4. Comparativo Didático: Pilha Tradicional XAMPP (PHP + Apache + MySQL) vs. Microframework Moderno (Flask + Python + SQLite)}

Muitos estudantes de desenvolvimento web iniciam seu aprendizado utilizando o pacote integrado \textbf{XAMPP} (\textit{Cross-Platform, Apache, MySQL, PHP, Perl}), que foi o padrão clássico da web durante décadas (e comum em disciplinas introdutórias de banco de dados e programação). Para compreender por que hoje utilizamos o \textbf{Flask} com a \textbf{Fetch API}, é fundamental contrastar essas duas abordagens:

\begin{itemize}[leftmargin=*]
  \item \textbf{Servidor Web \& Inicialização:} No modelo tradicional, o desenvolvedor precisa instalar o software XAMPP no sistema operacional, abrir seu painel de controle e iniciar o servidor \textbf{Apache} (que roda em segundo plano consumindo portas do sistema operacional como a 80 e a 443). No Flask, \textbf{não é necessário instalar nenhum servidor web externo}: o próprio interpretador Python cria um servidor HTTP de desenvolvimento embutido e de inicialização instantânea através do comando \texttt{app.run(port=5000)}.
  \item \textbf{Roteamento Físico vs. Roteamento Declarativo:} No PHP tradicional sobre o Apache, o roteamento de URLs está rigidamente atrelado à \textbf{árvore física de arquivos no disco}. Para acessar uma rota, a URL deve espelhar os diretórios do servidor (por exemplo, \texttt{http://localhost/meu-app/admin/listar.php} precisa obrigatoriamente apontar para o arquivo físico \texttt{listar.php}). No Flask, o roteamento é \textbf{lógico, semântico e desacoplado do sistema de arquivos}: decoradores como \texttt{@app.route('/api/produtos')} definem endereços elegantes independentemente de como o código está organizado internamente.
  \item \textbf{Monólito Acoplado vs. Arquitetura Desacoplada (API REST):} No fluxo clássico com PHP/XAMPP, o backend frequentemente realiza \textit{Server-Side Rendering} (renderização no servidor), mesclando lógica com código de apresentação (\texttt{echo '<tr><td>' . \$dado . '</td></tr>'}). Toda ação do usuário dispara um recarregamento completo da página web. Na arquitetura moderna que estamos construindo com Flask, o backend funciona exclusivamente como uma \textbf{API REST de dados puros (JSON)}; a interface visual é uma aplicação web rica (SPA) que roda no navegador do usuário e consome os dados de forma assíncrona (\texttt{fetch()}) sem recarregar a tela.
  \item \textbf{Banco de Dados \& Administração:} No XAMPP, utiliza-se o servidor de banco de dados MySQL/MariaDB (processo de rede separado) administrado via interface gráfica \textbf{phpMyAdmin}. No nosso projeto com Flask, adotamos o \textbf{SQLite 3}, cujo banco reside em um único arquivo local (\texttt{vitrine.db}) nativo da biblioteca padrão do Python, garantindo portabilidade absoluta (basta mover a pasta do projeto para levar o banco junto, sem senhas, usuários ou portas de rede para configurar).
\end{itemize}

\textbf{Por que instalamos o \texttt{flask-cors}?} Por medidas de segurança vitais, os navegadores implementam a \textbf{Política de Mesma Origem} (\textit{Same-Origin Policy - SOP}). Como a nossa página frontend roda na porta \texttt{5500} (Live Server) e o Flask escuta na porta \texttt{5000}, o navegador bloqueia a requisição a menos que o backend declare explicitamente a liberação de \textbf{CORS} (\textit{Cross-Origin Resource Sharing}) via cabeçalho \texttt{Access-Control-Allow-Origin: *}. A biblioteca \texttt{flask-cors} fornece o middleware que habilita essa autorização em apenas uma linha no Python: \texttt{CORS(app)}.

\subsubsection{Pílula 3: Envio de Dados com Fetch POST e JSON}

\textbf{Fundamentação Teórica:} Enquanto requisições \textbf{GET} servem para recuperar dados, o método HTTP \textbf{POST} transfere novas informações do cliente para persistência no servidor. 

Para enviar dados em formato JSON através da Fetch API, três etapas são mandatórias no objeto de configuração:
\begin{enumerate}[leftmargin=*]
  \item Declarar o método: \texttt{method: 'POST'};
  \item Declarar o cabeçalho HTTP: \texttt{headers: \{ 'Content-Type': 'application/json' \}}, avisando ao Flask que o corpo trafega em formato JSON;
  \item Serializar o objeto JavaScript em texto JSON puro: \texttt{body: JSON.stringify(dados)}.
\end{enumerate}

async function cadastrarNovoServico(evento, formCadastro, campoNome, campoPreco, feedbackPost) {
  evento.preventDefault();

  const dadosParaEnvio = {
    nome: campoNome.value.trim(),
    preco: parseFloat(campoPreco.value)
  };

  try {
    const resposta = await fetch('http://127.0.0.1:5000/api/cadastrar', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json'
      },
      body: JSON.stringify(dadosParaEnvio)
    });

    // Validação explícita sem contrações
    if (resposta.ok === false) {
      throw new Error(`O servidor retornou o código de erro: ${resposta.status}`);
    }

    const dadosResposta = await resposta.json();

    feedbackPost.className = 'alert alert-success mb-0';
    feedbackPost.classList.remove('d-none');
    feedbackPost.innerHTML = `
      <strong>${dadosResposta.mensagem}</strong><br>
      <small>ID gerado: #${dadosResposta.registro.id} | Total no servidor: ${dadosResposta.total}</small>
    `;

    formCadastro.reset();

  } catch (erro) {
    feedbackPost.className = 'alert alert-danger mb-0';
    feedbackPost.classList.remove('d-none');
    feedbackPost.innerHTML = `<strong>Falha ao enviar:</strong> ${erro.message}`;
  }
}

\subsubsection{Pílula 4: Resiliência de Rede e Feedback Visual (try/catch/finally com Spinner)}

\textbf{Fundamentação Teórica:} Em aplicações de produção, falhas de conectividade (servidor fora do ar, oscilação de Wi-Fi, erro 500) são inevitáveis. Uma aplicação de qualidade profissional precisa:
\begin{itemize}[leftmargin=*]
  \item Interceptar erros de rede com blocos \textbf{\texttt{try...catch}};
  \item Validar o status HTTP com a propriedade booleana \textbf{\texttt{resposta.ok}} (que retorna \texttt{true} apenas para códigos HTTP 200–299);
  \item Fornecer feedback visual instantâneo durante a espera (\textbf{Spinner de Carregamento} do Bootstrap);
  \item Utilizar obrigatoriamente o bloco \textbf{\texttt{finally}}, que é executado \textbf{sempre} (tanto em caso de sucesso quanto de falha), garantindo que o spinner seja ocultado e o botão reativado.
\end{itemize}

function ativarEstadoCarregando(elementos) {
  elementos.btnVerificar.disabled = true;
  elementos.iconeBotao.classList.add('d-none');
  elementos.spinnerCarregamento.classList.remove('d-none');
  elementos.textoBotao.textContent = 'Consultando Servidor...';
  elementos.caixaAlerta.classList.add('d-none');
}

function desativarEstadoCarregando(elementos) {
  elementos.spinnerCarregamento.classList.add('d-none');
  elementos.iconeBotao.classList.remove('d-none');
  elementos.textoBotao.textContent = 'Testar Conexão com o Servidor';

  elementos.caixaAlerta.classList.remove('d-none');
}

// 2. Função assíncrona nomeada com bloco defensivo try...catch...finally
async function testarConexaoComServidor(elementos) {
  ativarEstadoCarregando(elementos);

  try {
    const resposta = await fetch('http://127.0.0.1:5000/api/status');

    if (resposta.ok === false) {
      throw new Error(`O servidor retornou o código de erro HTTP ${resposta.status}.`);

function obterServicosLocal() {

export async function obterServicos() {
  try {
    const resposta = await fetch(`${API_BASE_URL}/servicos`, {
      method: 'GET',
      headers: { 'Accept': 'application/json' },
      signal: AbortSignal.timeout(3000)
    });
    if (!resposta.ok) throw new Error(`HTTP ${resposta.status}`);
    const dados = await resposta.json();
    apiConectada = true;
    localStorage.setItem(STORAGE_KEY, JSON.stringify(dados));
    return dados;
  } catch (erro) {
    apiConectada = false;
    console.warn('API Flask offline. Ativando contingência LocalStorage:', erro.message);
    return obterServicosLocal();
  }
}

export async function salvarServico(novoServico) {
  try {
    const resposta = await fetch(`${API_BASE_URL}/servicos`, {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'Accept': 'application/json'
      },
      body: JSON.stringify(novoServico),
      signal: AbortSignal.timeout(4000)
    });
    if (!resposta.ok) throw new Error(`HTTP ${resposta.status}`);
    const criado = await resposta.json();
    apiConectada = true;
    const servicos = obterServicosLocal();
    servicos.unshift(criado);
    localStorage.setItem(STORAGE_KEY, JSON.stringify(servicos));
    return criado;
  } catch (erro) {
    apiConectada = false;
    console.warn('Falha no envio à API. Salvando localmente:', erro.message);
    return salvarServicoLocal(novoServico);
  }
}

    apiConectada = false;
    console.warn('Falha na exclusão remota. Removendo localmente:', erro.message);
    removerServicoLocal(id);
    return true;
  }
}
